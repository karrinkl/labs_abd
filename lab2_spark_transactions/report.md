# 1. Цель работы

Цель работы — освоить распределённую обработку данных в Apache Spark: развернуть локальный кластер Spark Standalone (Master и Worker), обработать набор банковских транзакций средствами DataFrame API и Spark SQL, оценить качество и выполнить очистку данных, а также экспериментально сравнить время выполнения в локальном однопоточном режиме `local[1]` и в распределённом режиме.

Задачи работы:

1. Сгенерировать синтетический набор банковских транзакций с проблемами качества данных.
2. Развернуть кластер Spark Standalone в Docker Compose и подтвердить регистрацию Worker и работу executors.
3. Прочитать данные в Spark DataFrame с явной схемой, проверить качество и выполнить очистку.
4. Выполнить фильтрацию, группировку, агрегирование и сортировку согласно варианту № 2.
5. Определить города с самой высокой средней суммой транзакции с помощью Spark SQL.
6. Измерить и сравнить время выполнения в режимах `local[1]` и Spark Standalone, проанализировать причины результата.

# 2. Постановка задачи и вариант № 2

**Предметная область:** банковские транзакции.

**Обязательные поля набора данных:** `transaction_id`, `client_id`, `account_id`, `amount`, `currency`, `city`, `transaction_type`, `transaction_timestamp`. Дополнительно генерируется поле `channel` (канал проведения операции).

**Операции варианта № 2 (таблица 2.2 методички):**

| Операция | Реализация в проекте |
|---|---|
| Фильтрация | `amount_eur > x`, где x = 100 EUR (параметр `AMOUNT_THRESHOLD`) |
| Группировка и агрегирование | `groupBy("city")`: средняя сумма транзакции (`avg_amount_eur`) и количество транзакций (`transaction_count`) |
| Сортировка | по средней сумме транзакции по убыванию (`orderBy(avg_amount_eur DESC, city ASC)`) |
| Аналитика Spark SQL | города с самой высокой средней суммой транзакции (топ-5) |

Таблица 1 — Операции варианта № 2

**Принятые проектные решения:**

- **Приведение к одной валюте.** Суммы в исходных данных указаны в EUR, USD, GBP и CHF, а среднее по суммам в разных валютах не имеет смысла. Поэтому при очистке вычисляется `amount_eur = amount × курс`, где курсы — фиксированные условные коэффициенты (EUR 1,00; USD 0,92; GBP 1,17; CHF 1,05), а не рыночные котировки. Фильтр, среднее и SQL используют `amount_eur`; исходное поле `amount` (DECIMAL) сохраняется.
- **Набор для группировки** — **очищенный полный набор** транзакций, а не результат фильтра. Так же построен и SQL-запрос, что позволяет сверить результаты. Группировка по отфильтрованным данным (`amount_eur > 100`) рассчитывается дополнительно и сохраняется отдельно (`city_stats_over_threshold.csv`).
- Город `Unknown` (пропуск или нераспознанное значение) остаётся в очищенных данных, но в рейтинг городов не входит.

# 3. Краткая теория: Apache Spark и распределённые вычисления

**Apache Spark** — движок распределённой обработки данных. Программа описывает преобразования над распределёнными наборами данных; Spark строит из них ациклический граф (DAG), делит его на этапы и задачи и выполняет задачи параллельно на executors кластера, по возможности держа промежуточные данные в памяти. В отличие от классического MapReduce, многошаговая обработка не требует записи на диск между шагами, а весь запрос оптимизируется целиком.

**Архитектура приложения.** *Driver* — процесс с `SparkSession`: строит план, делит его на stages и tasks, планирует задачи и собирает результаты. *Executors* — JVM-процессы на рабочих узлах: выполняют задачи над партициями, хранят кэш и shuffle-данные. *Менеджер кластера* распределяет ресурсы. В работе используется Spark Standalone: Master принимает заявки приложений, Worker предоставляет ядра и память и запускает executors.

**Абстракции данных.** RDD — неизменяемая распределённая коллекция с линейкой происхождения (lineage), обеспечивающей восстановление потерянных партиций. DataFrame — распределённая таблица со схемой; его операции декларативны и оптимизируются Catalyst (логическая оптимизация, выбор физического плана, генерация кода). Типизированный Dataset API (`Dataset[T]`) доступен в Scala и Java. PySpark использует DataFrame API и Spark SQL.

**Ленивые вычисления.** Преобразования (transformations: `filter`, `withColumn`, `groupBy`, `orderBy`) только дополняют план. Выполнение запускают действия (actions: `count`, `collect`, `show`, `write`). Узкие преобразования выполняются конвейером внутри этапа. Широкие (группировка, сортировка, `distinct`, соединения) требуют shuffle — перераспределения данных между партициями через диск и сеть — и образуют границы этапов.

**Режимы запуска.** `local[1]` — драйвер и один поток выполнения задач в одной JVM. `local[*]` — локальный режим с числом потоков, равным числу доступных ядер (не однопоточный). `spark://host:7077` — подключение к кластеру Standalone, где задачи выполняют executors на Worker.

Ответы на контрольные вопросы, раскрывающие теорию подробнее, приведены в приложении А и в файле `control_questions.md`.

# 4. Описание датасета и способа генерации

Набор генерируется скриптом `generate_data.py` (только стандартная библиотека Python) и сохраняется в **CSV** с заголовком. CSV выбран, потому что его построчно читает Spark, файл делится на входные партиции по размеру, а некорректные значения естественно представляются строками.

| Поле | Тип в CSV | Содержание (синтетическое) |
|---|---|---|
| `transaction_id` | строка | `TX0000000001` … — уникальный номер |
| `client_id` | строка | `CL0000001` … (по умолчанию 1 клиент на 20 транзакций) |
| `account_id` | строка | `ACC000000001` …; у клиента 1–3 счёта, каждый в своей валюте |
| `amount` | строка (число) | логнормальное распределение по типу транзакции и городу, 2 знака после запятой |
| `currency` | строка | EUR (55 %), USD (25 %), GBP (12 %), CHF (8 %); в Лондоне и Цюрихе чаще GBP/CHF |
| `city` | строка | 12 европейских городов с разными весами и «типичным» уровнем сумм |
| `transaction_type` | строка | `payment`, `withdrawal`, `transfer`, `deposit` |
| `transaction_timestamp` | строка | `yyyy-MM-dd HH:mm:ss`, интервал [2025-01-01; 2026-01-01) UTC |
| `channel` | строка | `online`, `pos`, `atm`, `branch` (дополнительное поле) |

Таблица 2 — Поля набора данных

**Проблемы качества, вносимые генератором** (доли задаются параметрами):

- *пропуски* (`--missing-rate`, по умолчанию 2 % строк): пустое значение или строка из пробелов в одном из обязательных полей;
- *некорректные значения* (`--invalid-rate`, 1,5 %): отрицательная или нулевая сумма, нечисловая сумма (`abc`, `N/A`, `12,50`), неизвестная валюта (`XYZ`), неизвестный город (`Atlantis`), неизвестный тип операции, неразбираемая дата (`2025-13-45 25:61:00`), дата вне интервала (`2031-05-01`);
- *исправимые отклонения* (`--fixable-rate`, 2 %): лишние пробелы и другой регистр (`  berlin `, `PAYMENT`), валюта строчными буквами, альтернативный формат даты (`dd.MM.yyyy HH:mm:ss`, ISO с `T`);
- *дубликаты* (`--duplicate-rate`, 1 %): 60 % полные копии строк, 40 % частичные (тот же `transaction_id`, но другое оформление поля).

`--seed` (по умолчанию 42) обеспечивает воспроизводимость. Размер задаётся параметром `--rows` или переменной `DATA_ROWS`. Генератор сохраняет статистику в `data/<имя>.stats.json`.

| средний | `generate_data.py --rows 500000 --name transactions_medium` | 505 000 | 42,8 МБ | влияние размера |

# 6. Проверка качества исходных данных

Исходный CSV читается с **явной схемой**: все поля задаются как `StringType`. Это сделано намеренно: в данных есть нечисловые суммы и испорченные даты, а в Spark 4 по умолчанию включён режим ANSI, где обычный `CAST('abc' AS DECIMAL)` прерывает задание. Типы приводятся безопасно: `try_cast(amount AS DECIMAL(18,2))` и `try_to_timestamp` по трём допустимым форматам. Ошибка преобразования даёт NULL и флаг, а не исключение. Перед проверками значения нормализуются: обрезаются пробелы, пустая строка превращается в NULL, валюта приводится к верхнему регистру, тип и канал — к нижнему, город — `Initcap`.

`spark_job.py` выводит версию Spark, схему, первые строки и число строк, затем рассчитывает сводный отчёт одной агрегацией (`results/<набор>/quality_report.json`). Результаты основного набора (контрольный прогон):

# 7. Очистка данных

## 7.1 Правила и обоснование

| № | Этап | Правило | Обоснование |
|---|---|---|---|
| 1 | Полные дубликаты | `dropDuplicates` по всем исходным полям | повторная доставка одной и той же записи |
| 2 | Обязательные идентификаторы | строка без `transaction_id`, `client_id` или `account_id` отклоняется | без идентификаторов транзакцию нельзя проверить и учесть |
| 3 | Сумма | отклоняются: пропуск, нечисловой формат, значение ≤ 0 | сумма — анализируемая величина; восстановить её нельзя, подстановка исказила бы среднее |
| 4 | Время | отклоняются: пропуск, неразбираемое значение, выход за интервал; альтернативные форматы **приводятся** к `TIMESTAMP` UTC | неизвестное время не позволяет отнести операцию к периоду |
| 5 | Валюта | регистр **исправляется**; пропуск или неизвестный код — отклонение | без валюты нельзя пересчитать сумму в EUR |
| 6 | Город | регистр и пробелы **исправляются**; пропуск или нераспознанное значение → `Unknown` | сумма корректна и участвует в общих итогах; в рейтинг городов такие строки не входят |
| 7 | Тип и канал | регистр **исправляется**; пропуск или неизвестное значение → `unknown` | категория не влияет на корректность суммы |
| 8 | Частичные дубликаты | среди прошедших проверки строк с одинаковым `transaction_id` остаётся одна (сначала запись в основном формате даты, затем детерминированно по хешу) | выбор не зависит от разбиения на партиции, поэтому совпадает в разных режимах |

Таблица 7 — Правила очистки

Строки с любыми пропусками **не удаляются** без разбора: пропуск в городе, типе или канале исправляется меткой `unknown`. Удаляются только записи, которые нельзя корректно учесть. Каждая отклонённая строка получает **одну** причину — первую сработавшую проверку в порядке таблицы 7. Поэтому строка с несколькими дефектами не учитывается дважды. Отклонённые строки сохраняются вместе с причиной (`data/rejected_<набор>/`, примеры — `results/<набор>/rejected_sample.csv`) и не исчезают молча.

## 8.1 Фильтрация `amount_eur > x`

**Как `orderBy` влияет на выполнение.** Физический план (`results/transactions/plan_city_stats.txt`) для агрегации содержит цепочку `HashAggregate (partial) → Exchange hashpartitioning(city, 8) → HashAggregate (final) → Exchange rangepartitioning(avg_amount_eur DESC, city ASC) → Sort`:
- частичная агрегация уменьшает shuffle до одной строки на город в каждой партиции;
- глобальная сортировка добавляет **второй shuffle**: Spark выбирает границы диапазонов по выборке значений, перераспределяет строки так, чтобы каждая партиция содержала свой диапазон, и сортирует партиции локально.

Для 12 строк это дёшево. На полном DataFrame без предварительной агрегации глобальная сортировка перемещала бы весь набор между партициями. Кроме того, план очистки содержит ещё два shuffle: `dropDuplicates` и окно по `transaction_id`.

# 9. Реализация аналитики через Spark SQL

Очищенный DataFrame регистрируется как временное представление `transactions_clean`, после чего выполняется запрос (`results/transactions/top_cities.sql`):

```sql
SELECT city,
       AVG(amount_eur)           AS avg_amount_eur,
       ROUND(AVG(amount_eur), 2) AS avg_amount_eur_rounded,
       COUNT(*)                  AS transaction_count
FROM transactions_clean
WHERE city IS NOT NULL
  AND city <> 'Unknown'
  AND amount_eur IS NOT NULL
  AND amount_eur > 0
GROUP BY city
ORDER BY AVG(amount_eur) DESC, city ASC
LIMIT 5;
```

Сортировка выполняется по **точному** среднему, а округлённое значение выводится отдельным столбцом, поэтому округление не влияет на порядок. Если в данных меньше пяти городов, выводятся все доступные: `spark_job.py` проверяет это и печатает фактическое число.

Результат SQL построчно совпадает с первыми пятью строками DataFrame-агрегации (вывод `Результат SQL совпадает с DataFrame API: True`).

**Отличие от SQL в одной реляционной СУБД.** В обычной СУБД запрос исполняется одним сервером над данными, которыми он сам управляет: таблицы, индексы, статистика, транзакции. В Spark SQL:
- данные лежат во внешних файлах (CSV/Parquet) и читаются при выполнении;
- индексов нет;
- запрос превращается в распределённый план, который выполняют параллельно многие задачи на executors;
- группировка и сортировка выполняются через shuffle между партициями;
- представление `transactions_clean` — не таблица, а именованный логический план DataFrame.

**Роль Catalyst.** SQL-текст и DataFrame-код приводятся к одному логическому плану. Catalyst анализирует его (имена, типы), оптимизирует по правилам (проталкивание фильтров `city <> 'Unknown'` и `amount_eur > 0` ниже агрегации, отсечение неиспользуемых столбцов) и выбирает физический план; затем Tungsten генерирует код. Агрегация в SQL-запросе и в `city_stats()` планируется одинаково (`HashAggregate → Exchange → HashAggregate`). Для `ORDER BY … LIMIT 5` Catalyst выбирает оператор `TakeOrderedAndProject`: каждая партиция отдаёт свои 5 лучших строк, и полная глобальная сортировка не нужна. Это пример того, как оптимизатор учитывает весь запрос, а не отдельные операции.

# Приложение А. Ответы на контрольные вопросы

**1. Чем модель вычислений Spark принципиально отличается от MapReduce и за счёт чего растёт производительность?**

В классическом Hadoop MapReduce любое вычисление описывается парой фаз *map → reduce*. Результат каждой задачи записывается на диск (HDFS), а многошаговый алгоритм превращается в цепочку отдельных MapReduce-заданий, и между заданиями данные снова пишутся и читаются с диска.

Spark строит для всей программы один **ациклический граф операций (DAG)** из произвольных преобразований: `filter`, `groupBy`, `join`, оконных функций и т. д. Граф исполняется как набор этапов (stages). Внутри этапа узкие преобразования выполняются конвейером над одной партицией без промежуточной записи. Промежуточные данные можно держать в **оперативной памяти** (`cache()`/`persist()`) и переиспользовать.

Прирост производительности обеспечивают:
- отсутствие обязательной записи на диск между шагами и конвейерное исполнение внутри этапа;
- кэширование в памяти: важно для итеративных алгоритмов (ML) и повторных запросов к тем же данным;
- оптимизация всего плана целиком: Catalyst, генерация байт-кода Tungsten (whole-stage codegen), адаптивное исполнение AQE;
- долгоживущие executors: JVM не запускается заново для каждой задачи, как в MapReduce.

*Пример из проекта.* В `spark_job.py` исходный DataFrame `raw` кэшируется (`.cache()`). Проверки качества, очистка, фильтрация и агрегация используют его без повторного разбора CSV. В MapReduce это были бы несколько отдельных заданий, каждое со своим чтением с диска.

**2. Что такое RDD и какие его свойства обеспечивают надёжность и эффективность?**

**RDD (Resilient Distributed Dataset)** — неизменяемая, разбитая на партиции коллекция объектов, которая обрабатывается параллельно на узлах кластера. Это базовая абстракция Spark Core; DataFrame в итоге тоже исполняется как RDD (`df.rdd`).

Ключевые свойства:
- **Распределённость и партиционирование.** Данные разделены на партиции, каждую обрабатывает отдельная задача (task) на executor.
- **Неизменяемость (immutability).** Преобразование не меняет RDD, а создаёт новый. Это упрощает параллелизм и восстановление.
- **Линейка происхождения (lineage).** RDD хранит, из каких родительских RDD и какими операциями он получен. Потерянную партицию можно **пересчитать**, а не реплицировать заранее — отсюда «Resilient».
- **Ленивость.** Преобразования только записываются в граф; вычисление начинается при действии (action).
- **Управляемое хранение.** `persist()` с уровнями MEMORY_ONLY, MEMORY_AND_DISK и др.
- **Локальность данных.** Планировщик старается запускать задачу там, где лежит партиция.

Формально RDD задаётся пятью элементами: списком партиций, функцией вычисления партиции, зависимостями от родителей, а также (необязательно) партиционером и предпочтительными местоположениями.

**3. Роль DataFrame и Dataset; чем они отличаются от RDD с точки зрения оптимизации?**

**DataFrame** — распределённая таблица с именованными столбцами и **схемой** (аналог таблицы реляционной БД). **Dataset** — типизированный вариант той же абстракции: в Scala `DataFrame = Dataset[Row]`, а `Dataset[T]` работает с объектами класса `T` и проверяет типы при компиляции.

Отличия от RDD:
- Для RDD Spark видит лишь «чёрные ящики» — пользовательские функции над произвольными объектами — и не может их оптимизировать. Для DataFrame/Dataset операции описаны **декларативно** (выбрать столбцы, отфильтровать, сгруппировать) и схема известна. Поэтому оптимизатор **Catalyst** может переставлять фильтры, отбрасывать ненужные столбцы, выбирать стратегию соединения.
- Данные хранятся в компактном бинарном формате **Tungsten** (вне Java-объектов), а для этапов генерируется байт-код, что уменьшает нагрузку на GC и потребление памяти.
- В PySpark операции DataFrame выполняются **в JVM**. Данные не передаются в Python-процессы, если не использовать Python-UDF; с RDD в PySpark каждая лямбда выполняется в Python-воркере с сериализацией.

**Важно про PySpark.** Типизированный Dataset API (`Dataset[T]` с case-классами и encoders) существует только в **Scala и Java**. В Python статической типизации таких классов нет, и PySpark использует **DataFrame API** (и Spark SQL), не предоставляя типизированный Dataset в той же форме. Поэтому проект написан на DataFrame API и встроенных функциях `pyspark.sql.functions`, без UDF.

**4. Архитектура приложения Spark: Driver и Executors**

- **Driver** — процесс с функцией `main` приложения и объектом `SparkSession`/`SparkContext`. Driver:
  - строит логический и физический план;
  - делит DAG на stages и tasks;
  - через **менеджер кластера** запрашивает ресурсы;
  - планирует задачи на executors, отслеживает их выполнение и собирает результаты действий (`collect`, `count`);
  - поднимает Spark UI (порт 4040).
- **Executors** — JVM-процессы на рабочих узлах. Они выполняют задачи над партициями, держат кэшированные данные (BlockManager), пишут и читают shuffle-файлы и отчитываются драйверу о статусе и метриках.
- **Менеджер кластера** (в проекте — Spark Standalone: Master и Worker) выделяет ресурсы. Worker запускает executors по указанию Master.

Взаимодействие в проекте:
1. `spark-submit` в контейнере `spark-client` запускает драйвер.
2. Драйвер регистрирует приложение у `spark-master:7077`.
3. Master поручает `spark-worker` запустить executor с 2 ядрами и 1 ГБ памяти.
4. Executor подключается **обратно к драйверу** (`spark.driver.host=spark-client`).
5. Драйвер рассылает задачи, а executor читает `/opt/project/data/*.csv` из общего тома.

В режиме `local[1]` драйвер и единственный поток задач находятся в одной JVM. Поэтому REST API показывает только executor `driver`.

**5. Что такое ленивые вычисления и какие преимущества они дают?**

**Lazy Evaluation** — преобразования (`filter`, `withColumn`, `groupBy`…) не выполняются сразу, а только добавляются в логический план. Вычисление запускается, когда вызывается **действие**, которому нужен результат.

Преимущества:
- оптимизатор видит **весь** запрос целиком. Он может протолкнуть фильтр ближе к источнику, отбросить неиспользуемые столбцы (column pruning), объединить проекции и выбрать тип соединения;
- конвейерное выполнение узких операций за один проход по данным;
- не вычисляется то, что не нужно: `limit`/`show` читают только часть данных;
- линейка операций служит основой отказоустойчивости.

*Пример.* В `transactions_pipeline.clean()` десятки `withColumn` (нормализация, `try_cast`, `try_to_timestamp`), `dropDuplicates`, оконная функция и фильтры не выполняют ни одной задачи. Работа начинается только в `stats.collect()` в `benchmark_pipeline` или в `count()` в `spark_job.py`.

**6. Transformations и Actions — разница и примеры**

- **Transformation** возвращает новый DataFrame/RDD и лениво дополняет план. Примеры из проекта: `filter(F.col("amount_eur") > x)`, `withColumn("amount_dec", ...)`, `groupBy("city").agg(...)`, `orderBy(...)`, `dropDuplicates(...)`, `select`, `unionByName`.
- **Action** запускает вычисление и возвращает результат драйверу или пишет его во внешнюю систему. Примеры: `count()`, `collect()`, `show()`, `write.parquet(...)`, `take(n)`.

Каждое действие порождает одно или несколько **заданий (jobs)** в Spark UI.

**7. Narrow и Wide Transformations — какая дороже и почему**

- **Узкие (narrow)**: каждая выходная партиция зависит от **одной** входной. Обмен данными между узлами не нужен, операции объединяются в один этап. Примеры: `filter`, `select`, `withColumn`, `map`, `union`.
- **Широкие (wide)**: выходная партиция зависит от **многих** входных. Данные нужно перераспределить по ключу (shuffle), и граница такого преобразования начинает новый этап. Примеры: `groupBy().agg()`, `orderBy`, `distinct`/`dropDuplicates`, `join` (кроме broadcast), оконные функции с `partitionBy`, `repartition`.

**Широкие дороже**: они требуют записи промежуточных данных на диск, передачи по сети, десериализации и синхронизации — этап не начнётся, пока не завершится предыдущий.

*В проекте* физический план (`results/<набор>/plan_city_stats.txt`) содержит несколько узлов `Exchange` — это shuffle:
- `dropDuplicates` — `hashpartitioning` по всем полям;
- окно по `transaction_id` — `hashpartitioning(transaction_id_n)`;
- `groupBy("city")` — `hashpartitioning(city)`;
- `orderBy` — `rangepartitioning(avg_amount_eur DESC, city ASC)`.

**8. Что такое Shuffle, когда он возникает и как влияет на производительность?**

**Shuffle** — перераспределение данных между партициями (и узлами) так, чтобы записи с одинаковым ключом или из одного диапазона оказались в одной партиции. Задачи предыдущего этапа (map side) пишут данные, разбитые по целевым партициям, в локальные shuffle-файлы. Задачи следующего этапа (reduce side) забирают свои блоки по сети у всех executors.

Возникает при широких преобразованиях: группировках, `distinct`, сортировке (`orderBy` — range partitioning с предварительной выборкой границ), соединениях по ключу, `repartition`, оконных функциях с `partitionBy`.

Влияние на производительность:
- дисковый и сетевой ввод-вывод, сериализация;
- этап-барьер: новый этап ждёт завершения всех задач предыдущего;
- перекос ключей (skew): одна большая партиция тормозит весь этап;
- неудачное число shuffle-партиций (`spark.sql.shuffle.partitions`). Если их слишком много, растут накладные расходы на мелкие задачи; если слишком мало — недогружены ядра и высок риск нехватки памяти.

*В проекте:*
- `groupBy("city")` сначала выполняет **частичную агрегацию** на каждой партиции (`HashAggregate` partial). Поэтому через shuffle передаётся лишь по одной строке на город и партицию, а не все транзакции.
- Самые объёмные shuffle — `dropDuplicates` и окно по `transaction_id`: они перемещают почти весь набор.
- Значение `spark.sql.shuffle.partitions=8` задано в `.env` одинаковым для всех режимов. AQE может дополнительно объединить мелкие партиции.

**9. Для чего нужен DAG и как он связан с разделением на Stages?**

DAG (Directed Acyclic Graph) — граф зависимостей между RDD/операциями физического плана. Получив действие, **DAGScheduler** обходит граф от результата к источникам и **режет его на stages по границам широких зависимостей** (shuffle). Внутри stage все узкие операции выполняются конвейером. Stage состоит из tasks — по одной на партицию. Stages с готовыми shuffle-результатами можно пропустить (в UI — *skipped*), например при повторном использовании кэша.

DAG также даёт отказоустойчивость: зная зависимости, Spark пересчитывает только потерянные партиции.

*В проекте* задание `collect()` для рейтинга городов в Spark UI (вкладка **Jobs → DAG Visualization**) включает этапы:
1. чтение CSV и частичная дедупликация;
2. окно по `transaction_id`;
3. агрегация по городам;
4. сортировка.

Этапы, результаты которых уже есть (например, чтение закэшированного `raw` в `spark_job.py`), могут отображаться как skipped.

**10. Какую функцию выполняет оптимизатор Catalyst?**

**Catalyst** — расширяемый оптимизатор Spark SQL, общий для DataFrame API и SQL. Запрос проходит этапы:
1. **Анализ.** Неразрешённый логический план связывается с каталогом и схемой: имена столбцов и таблиц, типы.
2. **Логическая оптимизация** по правилам: проталкивание предикатов (predicate pushdown), отсечение столбцов, свёртка констант, упрощение выражений, удаление лишних проекций и сортировок.
3. **Физическое планирование.** Генерация вариантов (например, sort-merge join или broadcast hash join) и выбор по стоимостной модели.
4. **Генерация кода** (Tungsten whole-stage codegen) — байт-код JVM для этапов.

В Spark 3+/4 к этому добавляется **AQE**: план корректируется по фактической статистике shuffle. AQE объединяет мелкие партиции и меняет стратегию соединения.

*Пример.* SQL-запрос `top_cities.sql` и DataFrame-функция `city_stats()` написаны по-разному, но Catalyst приводит их агрегацию к одной схеме: `HashAggregate (partial) → Exchange hashpartitioning(city) → HashAggregate (final)`. Различается только верх плана. Для DataFrame без ограничения нужна глобальная сортировка (`Exchange rangepartitioning → Sort`). Для SQL с `ORDER BY … LIMIT 5` Catalyst выбирает оператор `TakeOrderedAndProject`, который берёт лучшие строки каждой партиции без полной сортировки. Результаты совпадают — это проверяет `spark_job.py` («Результат SQL совпадает с DataFrame API: True»).

**11. Почему схему лучше задавать явно, а не полагаться на автоматический вывод?**

- `inferSchema=true` требует **дополнительного прохода** по данным (полностью или по выборке), что для больших CSV дорого.
- Выведенные типы **нестабильны**. Одна строка `"abc"` в столбце сумм делает весь столбец `string`, а при другом наборе данных тип станет `double`. Последующий код начинает вести себя иначе.
- Явная схема — это **контракт**: имена, порядок и типы столбцов зафиксированы, ошибки обнаруживаются сразу.
- Можно осознанно выбрать точные типы (`DECIMAL(18,2)` для денег вместо `double`) и управлять обработкой некорректных записей.

*В проекте* `RAW_SCHEMA` задаёт все поля исходного CSV как `StringType` намеренно: исходные данные «грязные». Затем типы приводятся **безопасно** — `try_cast(amount AS DECIMAL(18,2))` и `try_to_timestamp` по трём форматам. Строки с ошибками получают причину `invalid_amount_format` или `invalid_timestamp` и попадают в набор отклонённых, а не роняют задание. Это особенно важно в Spark 4, где по умолчанию включён режим ANSI: обычный `CAST('abc' AS DECIMAL)` вызвал бы ошибку.

**12. Суть партиционирования и влияние числа партиций на параллелизм**

Партиция — единица параллелизма: одна задача обрабатывает одну партицию на одном ядре. Число партиций определяет, сколько задач этапа может выполняться одновременно, и сколько их будет всего:
- **мало партиций** (меньше числа ядер): часть ядер простаивает; большие партиции рискуют не поместиться в память и дают долгие «хвосты»;
- **слишком много мелких партиций**: накладные расходы на планирование, запуск задач и мелкие shuffle-файлы превышают полезную работу;
- практическое правило — в 2–4 раза больше партиций, чем ядер, при размере партиции порядка десятков–сотен МБ.

Источники партиций в проекте:
- при чтении CSV — `spark.sql.files.maxPartitionBytes` (32 МБ в `.env`): основной файл ~171 МБ даёт несколько входных партиций, тестовый (0,9 МБ) — одну;
- после shuffle — `spark.sql.shuffle.partitions` (8) с учётом объединения партиций AQE.

Число партиций записывается в `results/benchmark/summary.csv` (столбцы `input_partitions`, `shuffle_partitions`). Для тестового набора одна входная партиция означает, что два ядра кластера на первом этапе использовать нельзя.

**13. Почему распределённое выполнение небольшого набора может быть медленнее `local[1]`?**

Для маленьких данных полезная работа занимает доли секунды, а фиксированные накладные расходы распределённого режима — сопоставимое или большее время:
- запуск приложения: регистрация у Master, запуск JVM executor на Worker, подключение executor к драйверу (в проекте измеряется отдельно как `session_start_s`);
- сериализация задач и их рассылка по сети, RPC-сообщения о статусе каждой задачи;
- shuffle через сетевой стек (даже между контейнерами одного хоста) вместо обмена внутри одной JVM;
- передача результатов на драйвер;
- малое число партиций: при одной входной партиции дополнительные ядра бесполезны.

В `local[1]` всё выполняется в одной JVM: нет сети между драйвером и executor, задачи запускаются мгновенно. Поэтому на тестовом наборе (≈10 тыс. строк) кластер может проиграть. Выиграть он может на наборе, где объём вычислений достаточно велик, чтобы параллельная работа нескольких ядер перекрыла накладные расходы. Это не гарантируется и определяется экспериментом (`benchmark.py`, таблица в `report.md`).

**14. Какие метрики Spark UI полезны для анализа производительности и поиска узких мест?**

- **Jobs / Stages**: длительность заданий и этапов, число задач, DAG-визуализация, skipped stages.
- **Stage detail**: распределение длительности задач (min/median/max) — признак перекоса; Input Size / Records; Shuffle Read и Shuffle Write (объём и записи); **Spill (memory/disk)** — нехватка памяти; GC Time; Scheduler Delay; Task Deserialization Time; Result Serialization Time; Event Timeline.
- **Executors**: число executors, ядер, использованная и доступная память хранения, активные, завершённые и неудачные задачи, общее время задач и время GC, объём shuffle, пиковое потребление памяти JVM.
- **Storage**: закэшированные DataFrame/RDD и их размер в памяти и на диске.
- **SQL / DataFrame**: граф физического плана с метриками узлов (число строк на выходе `Exchange`, `HashAggregate`, время), детали AQE.
- **Environment**: фактические параметры конфигурации.

Те же данные доступны через REST API `http://<драйвер>:4040/api/v1/applications/<appId>/...`. Проект использует его в `transactions_pipeline.rest_get()`: `benchmark.py` суммирует `executorRunTime`, `executorCpuTime` и `shuffleWriteBytes` по этапам измеряемых прогонов и записывает пиковую память JVM executors.

**15. Как Spark обеспечивает отказоустойчивость и что произойдёт при отказе одного Executor?**

Механизмы:
- **Lineage и детерминированный пересчёт.** Неизменяемые партиции можно восстановить, повторив преобразования от источника или от последнего сохранённого shuffle-результата.
- **Повтор задач.** Упавшая задача перезапускается (до `spark.task.maxFailures`, по умолчанию 4 попытки), в том числе на другом executor.
- **Повтор этапов.** Если пропали shuffle-файлы (их хранил потерянный executor), DAGScheduler получает `FetchFailed` и пересчитывает недостающие партиции предыдущего этапа.
- **Checkpointing** (`checkpoint()`) обрывает слишком длинную линейку, сохраняя данные в надёжное хранилище; для Structured Streaming — checkpoint состояния и offset.
- Реплицируемые уровни хранения (`MEMORY_ONLY_2`) для кэша.
- В Standalone Master перезапускает executors на доступных Worker. Для отказоустойчивости самого Master предусмотрен режим standby-мастеров через ZooKeeper (в учебном кластере не настроен).

**При отказе одного executor:**
1. Драйвер перестаёт получать heartbeat и помечает executor потерянным.
2. Выполнявшиеся на нём задачи и его кэшированные блоки считаются потерянными.
3. Задачи перезапускаются на других executors. Если других нет, Master просит Worker запустить новый executor (при наличии ресурсов).
4. Если терялись shuffle-выходы, перевычисляются нужные задачи предыдущего этапа.
5. Задание продолжается и завершается с правильным результатом, но дольше.

Отказ **драйвера** означает отказ всего приложения в режиме client. В учебном кластере с одним Worker при остановке контейнера `spark-worker` задачи будут ждать, пока Worker не вернётся и не зарегистрируется снова.
